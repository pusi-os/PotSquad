## 0. Почему v2 и что было не так в v1

Разбор 2026-10-18 (провод сверен по коду четырёх реализаций):

| Проблема v1 | Следствие |
|---|---|
| Реестр `kind` разошёлся: `11/12` = HEADSUP/FIX в PotSquad против SACK/REPAIR у BroWatch/App/ComPiXi | ложная интерпретация кадров (одинаковая длина 19Б) |
| Presence не переносит стабильной личности | привязка к MAC; RPA на телефонах рождает «призраков» и ломает nonce |
| nonce = наблюдаемый MAC | прошивка не открывает кадры телефона (Android прячет адрес → `02:00:00:00:00:00`) |
| Нет TTL/hop в проводе | relay возможен только эвристикой по времени; хопы недоказуемы |
| Нет контейнера расширений у прошивки | DM/файлы/почта/`nodeId` — только у приложений |
| Разные лимиты текста (3 части у прошивки, 15 у app) | кириллица и длинные сообщения теряются |

Вывод: **чистый v2 без обратной совместимости**, но с аддитивно расширяемым
контейнером, стабильной личностью и маршрутизацией в проводе.

## 1. Лучшие практики, на которые опираемся

- **Managed flooding (Meshtastic / compixi MeshRelay).** Каждый узел
  ретранслирует до hop-лимита; слушает эфир перед ретрансляцией (contention
  по RSSI: дальние несут первыми); услышал чужой релей — молчит
  (overhear-suppression); «услышал свою копию = доставлено» для broadcast.
- **Path/reliable-слой (MeshCore / compixi MeshReliable).** SACK-битмап,
  REPAIR-дыры, окно отправителя, RTO с экспоненциальным backoff, token-bucket
  duty-cycle. Broadcast не подтверждается поштучно (шторм) — вместо ACK
  используется релей-подтверждение + финальный SACK.
- **Сквозная адресация, а не адрес звена (Reticulum/LXMF).** Личность —
  криптографическая (наш `nodeId` + ключ фразы), адрес звена эфемерен.
- **Разделение чистого и радио (Карпати).** Кодеки — арифметика над байтами,
  компилируется и тестируется на хосте; транспорт — отдельный слой за
  интерфейсом (`mesh_transport.h` как образец).
- **Принимай старое — шли новое** там, где это бесплатно; здесь — новый
  magic/версия, старые кадры просто дропаются.
- **Расширяемость через контейнер.** Один `EXT`-kind + реестр подвидов;
  неизвестный подвид дропается молча, провод не меняется.
- **Доказуемость.** Golden-векторы из независимой реализации (Python
  `cryptography`) на каждый кадр; негативные тесты на каждый отказ.

Правовой контур (см. `docs/LORA.md` §8): 2.4 ГГц BLE/ESP-NOW — general
licence без duty-cycle; LoRa — только SRD **868 МГц** с duty-cycle
(869.4–869.65 = 500 мВт/10 % — лучший выбор); **любительские полосы 70 см
запрещены** (шифрование). Это вшивается в транспортный профиль LoRa.

## 2. Архитектура (слои)

```
┌──────────────────────────────────────────────────────────────┐
│ App payload: presence·chat·emote·DM·control·mailbox·blob·voice│
├──────────────────────────────────────────────────────────────┤
│ MeshFrame  — sealed AEAD, стабильный nonce от nodeId          │  (чистый кодек)
├──────────────────────────────────────────────────────────────┤
│ MeshEnvelope — маршрутизация: ttl/hop/trace (изменяемые) +    │  (чистый кодек)
│                routeTag (неизменяемое, аутентифицируемое)      │
├──────────────────────────────────────────────────────────────┤
│ Transport adapter: BLE-ADV · BLE-GATT · ESP-NOW · LoRa · MQTT  │  (радио)
└──────────────────────────────────────────────────────────────┘
```

Два режима передачи:
- **Режим C (compact, BLE-ADV):** только `MeshFrame` (≤27Б) под company
  `0xFFFF`; одиночный хоп; личность берётся из присутствия (карта
  `linkAddr→nodeId`). Релей на BLE — ретрансляция тех же байт + служебный
  AD `PER1` с ttl/hop/хэшем кадра (управляет хопами, не трогая кадр).
- **Режим E (envelope, ESP-NOW/LoRa/MQTT/BLE-GATT):** полный `MeshEnvelope`,
  настоящий managed flood с TTL и трассой.

## 3. Личность и крипто (без привязки к MAC)

- **`nodeId` — 8 случайных байт**, генерируются один раз, хранятся вечно:
  NVS `pusimesh/nodeid` (прошивка), `SharedPreferences("mesh")/nodeId`
  (Android), `config` (PixelDesk). Это **логическая личность**; MAC — только
  текущий адрес звена.
- **`linkAddr → nodeId`** — таблица соответствия, наполняется из presence
  (ble-адрес → заявленный nodeId), с TTL и freshest-wins. RPA ротируется —
  запись перепривязывается, призраков нет.
- **`squadTag` (3Б)** = `SHA256(squadKey ‖ "pusimesh/v2/squad")[0:3]` —
  позволяет релею проверять членство, не расшифровывая кадр.
- **`nodeShortTag` (2Б)** = `nodeId[6:8]` — метка хопа в трассе.
- Ключ: `squadKey = PBKDF2-HMAC-SHA256(phrase, "pusimesh/v2/key", 20000) → 16Б`.
- `routeKey = HMAC-SHA256(squadKey, "pusimesh/v2/route")[0:16]`.
- **Кадр:** AES-128-CCM, tag 8. **nonce = `nodeId[0:6] ‖ counter[3 LE] ‖ 0×4`**
  (13Б). Стабилен при смене адреса — проблема телефонов исчезает.
- **counter** — 24 бита, сквозной на отправителя, персист **до** использования
  (блок 64), отказ при исчерпании.

## 4. Провод

### 4.1 Presence v2 (broadcast, ~1.5с)
```
[0..1]  company 0xFFFF (LE)         (в BLE — manufacturer id)
[2..5]  magic 'P','M','2'
[6]     version = 2
[7]     flags: 0x01 имя-кастом, 0x02 phone/companion, 0x04 групповая роль…
[8..15] nodeId (8)
[16..18] squadTag (3)
[19..20] appearance word (LE): nick(4)|outfit(5)|shade(2)|custom(1)|aura(1)|spare
[21]    capability bitmap: bit0 EXT, bit1 blob, bit2 voice, bit3 relay, …
[22..]  имя (0..12Б, UTF-8, по границе символа) — только если flags&1
```
Длина: 22 без имени, 34 с именем. В ESP-NOW/режим E — с запасом; в BLE-ADV —
**короткая форма** (без имени = 22Б) или split на два AD
(`PM2` presence + `PEX` расширение), чтобы влезть в 31Б. Детали — в задании
транспорта.

### 4.2 MeshFrame (sealed, оба режима)
```
[0..1]  'P','U'
[2]     ver(4) | kind(4)      (ver = 2)
[3..5]  counter u24 LE
[6..]   ciphertext
[..]    tag[8]
```
AAD = байты 0..5. nonce — см. §3. Минимальный кадр (canned, ct=1) = 15Б;
+company 2 = 17Б ≤ 31 (BLE-ADV). Текст-часть ct=13 → 27Б; +2 = 29 ≤ 31 ✓.

### 4.3 MeshEnvelope (режим E)
```
[0..1]   'P','E'
[2]      version = 2
[3]      flags: DM 0x01 | BC 0x02 | LASTMILE 0x04 | ACK 0x08 | AUTH 0x10 | FRAG 0x20
[4]      ttlMain   (0..8)
[5]      ttlLast   (0..16)
[6..8]   squadTag (3)
[9..16]  srcNode (8)
[17..24] dstNode (8)   (all-FF = вещание скваду)
[25..28] msgId u32 BE  (случайный)
[29]     partIdx(4) | partTotal(4)
[30]     hopCount   (= число трасс-меток ниже)
[31..]   trace[hopCount] × u16 (nodeShortTag)
[..]     MeshFrame (sealed)
[..]     routeTag[8]  (если AUTH): HMAC-SHA256(routeKey, routeAad)[0:8]
```
`routeAad = "pusimesh/route/v2" ‖ flags(immutable) ‖ srcNode ‖ dstNode ‖ msgId
‖ partIdx ‖ partTotal`. ttl/trace намеренно **не** входят: их меняет релей.
Это и есть «управляемое поле вне AEAD» (урок Meshtastic).

Оверхеды: HDR 31Б + 2×trace + frame(15..27) + 8 = 66..84Б (без трассы);
ESP-NOW v1 usable ~230Б → с 24 хопами (~48Б) ~180Б — влезает.

### 4.4 Реестр `kind` (v2, чистый)
| kind | имя | примечание |
|---|---|---|
| 0x0 | EXT | контейнер расширений (см. 4.5) |
| 0x1 | CANNED | индекс строки |
| 0x2 | TEXT | короткий, 1 часть, ≤16 симв. |
| 0x3 | EMOTE | emote + setup |
| 0x4 | HELLO | версия + часы + зона |
| 0x5 | READ | base24 + tag4 (привязка к читателю) |
| 0x6 | SACK | base24 + mask16 |
| 0x7 | REPAIR | base24 + missing16 |
| 0x8 | TEXT_LONG | multi-part, флаг алфавита внутри |
| 0x9 | CONTROL | состояние управляемой передачи |
| 0xA | IDENTITY | nodeId + имя + caps (sealed) |
| 0xB | CONFIRM | base24 + tag4 (машинное «дошло целиком») |
| 0xC | ROUTE_PROBE | ping/echo для диагностики маршрута (опц.) |
| 0xD..0xF | резерв | |

Текстовые алфавиты (латиница + кириллица, 6-бит, 16/часть) — общие; флаг
алфавита в байте части. `TEXT_MAX = 240` (15 частей) везде.

### 4.5 EXT-подвиды (единый реестр)
```
1  DM              12 MSG_QUERY      23 FIX
2  FILE_MANIFEST   13 MSG_SUMMARY    24 RC_CHALLENGE
3  FILE_CHUNK      14 MSG_FETCH      25 RC_ACK
4  FILE_ACK        15 MSG_CHUNK      26 RADAR_SIGHT
5  FRIEND_REQ      16 MSG_ACK        27 CAPS
6  FRIEND_RESP     17 IDENTITY       28 NUDGE
7  CONFIRM         18 PRESENCE_EXT   29 WIFI
8  BLOB_MANIFEST   19 HEADS_UP       30 UPDATED
9  BLOB_CHUNK      20 RC_* (рез.)    31.. резерв
10 BLOB_ACK        21 VOICE_FRAME
11 VOICE_MANIFEST  22 RC_ACK_ALT
```
Неизвестный подвид — молча дроп (провод не меняется).

### 4.6 Языки, кириллица и имена (гарантия)

**Сообщения.** В v2 алфавит сообщения выбирается по тексту, а не по языку
борды, и шлётся **флагом внутри кадра** (§4.4). Кириллический набор:
33 заглавные буквы + пробел + 10 цифр + `.,?!'-` = **51 код ≤ 64** — влезает
в 6-битный код без потерь. `TEXT_MAX = 240` символов (15 частей × 16) для
латиницы и кириллицы одинаково. Никаких `?` и обрезаний: код, которого нет
в таблице приёмника, — только версия-скью, а не наша норма. Смешанный текст
(латиница + кириллица) кодируется кириллическим набором (в нём есть и
латиница как отдельные коды? — нет, поэтому смешанный текст шлётся двумя
частями с разным алфавитом; реализуемо на Ф2, покрыто тестом).

**Имена.** Presence v2 несёт имя как **UTF-8** с обрезкой по границе
символа (2 байта на кириллическую букву). Бюджет в BLE-ADV ограничен 31Б,
поэтому:
- индексированные имена (10 ников) — **локализуются на устройстве**, в эфир
  идёт индекс (0 байт на язык);
- кастомное имя в presence — до 12Б = 6 кириллических букв (как v1);
- **полное длинное имя** (до 63Б = ~31 кириллическая буква) едет отдельным
  sealed-кадром `IDENTITY` (kind 0xA / EXT 17), при необходимости частями;
  ростер хранит его и рисует. Никакого MAC/`PEER-xxxx` в табличке.

**Весь остальной русский** (меню, подписи, реплики персонажа, каннед-строки,
эмодзи-названия, диагностика) **не передаётся по проводу** — это локальные
строки; язык выбирается тумблером, а покрытие глифов — вопрос шрифтов
(RuCyr8/RuCyr16), уже решённый в прошивке. Провод от языка не зависит.

**Тесты.** Golden-векторы на русскую строку (короткую и 15 частей), на
имя в кириллице (граница UTF-8, 6 и 12 букв), на смешанный набор.

## 5. Надёжность и маршрутизация

### 5.1 Managed flood (как compixi `MeshRelay`)
- seen-cache 32+: `(srcNode, msgId, partIdx)`; ACK-before-dedup.
- last mile: `F_LASTMILE` несут только члены (по `squadTag`); узел с
  `ttlMain==0` конвертирует в `ttlLast=16`.
- contention-окно по RSSI: слабый −20..60мс, средний 50..120, сильный
  80..200 + джиттер; услышал ту же копию — отменил релей (k=1).
- своё не ретранслируем; релей требует TRANSMIT, доставка — MESSAGES.
- DM — `F_ACK` обратным флудом (ttl = hopsUsed+2); BC — неявный ACK релеем.

### 5.2 ARQ и состояния (как compixi `MeshReliable`)
- Отправитель: окно 4, `SACK_DELAY=350мс`, RTO 4с→30с (×2), `RETRIES_MAX=3`,
  состояния `SENDING→RELAYED→DELIVERED|FAILED`.
- Получатель: битмап частей, REPAIR-дыры, `RECEIVE_AGE=90с`.
- UI-состояния: `SENT ✓ → MESH ✓✓ → READ ✓✓(акцент) → FAILED ⚠`, ручной
  «переслать» тем же `msgId`/base.

### 5.3 Store-and-forward + почта (то, что просил заказчик)
- Любой узел, аутентифицировавший **групповой** кадр, который не может
  доставить (или BC), МОЖЕТ положить его в **bounded mailbox-хранилище**
  (sealed-байты + `(srcNode,msgId,partIdx)` + TTL 30 мин, ёмкость напр. 64).
- **DM хранит только отправитель** (в своём outbox) — получатель-посредник
  ключа не имеет; приватность by design.
- Флоу «спросить у ближайшего соседа про непрочитанное»:
  1. клиент вещает `EXT MSG_QUERY` (sealed): `[ownNodeId 8][perSenderHW…]`
     — «что у тебя есть новее моей отметки, для меня или для сквада?».
  2. держатель отвечает `EXT MSG_SUMMARY`: `[count][msgId…][srcNode…]`.
  3. клиент `EXT MSG_FETCH`: `[msgId…]`.
  4. держатель `EXT MSG_CHUNK`: **побайтовый replay** исходного sealed-кадра.
  5. клиент `EXT MSG_ACK` — держатель снимает запись.
- Дедуп/анти-реплей: `(srcNode,msgId,partIdx)` + seen-cache; получатель
  дедупит по `(srcNode, base)` и по хэшу собранного.
- Запрос ходит по хопам (envelope ttl), поэтому «у ближайшего» ≠ «напрямую».

### 5.4 Чанкинг и блобы (файлы/голос)
- Envelope уже несёт `partIdx|partTotal` — базовое дробление на любом
  транспорте.
- `EXT BLOB_MANIFEST/CHUNK/ACK`: `[blobId u32][size u32][sha8][kind]
  [chunkSize u16][chunkCount u16][name…]`; чанки `[blobId][seq u16][bytes][crc16]`;
  ACK — битмап, `MISSING` после DONE. Resume по байт-офсету (не по «чанкам
  профиля»), финальный SHA-256.
- Выбор транспорта: BLE-GATT / TCP(PusiServer) для крупного; ESP-NOW/LoRa —
  небольшие блобы и голос; BLE-ADV — только малые (текст, анонсы).
- Голос — см. §5.5 (отдельный слой поверх bLOB).

### 5.5 Голосовые сообщения (10–15 с, надёжно)

Это **voice message** (запись → доставка → прослушивание), а не live-PTT.
Доставка отложенная и подтверждаемая, поэтому допускает секунды-минуты и
хранится почтой (§5.3). Опциональный live-PTT — за горизонтом, отдельно.

**Кодеки и размеры (mono, 10/15 с):**
| Профиль | Битрейт | 10 с | 15 с | Где уместен |
|---|---|---|---|---|
| Opus 16 кГц VOIP (по умолчанию) | 12–16 кбит/с | 15–20 КБ | 22–30 КБ | BLE-GATT, TCP, ESP-NOW |
| Opus 8 кГц узкополосный | 8–10 кбит/с | 10–12 КБ | 15–19 КБ | ESP-NOW, слабый канал |
| Codec2 3200 | 3,2 кбит/с | 4 КБ | 6 КБ | LoRa / очень узкий канал |
| Codec2 1300 | 1,3 кбит/с | 1,6 КБ | 2,4 КБ | крайний минимум |

Дефолт — **Opus 16 кГц, ~16 кбит/с**, лимит клипа **15 с**, потолок размера
32 КБ. Профиль выбирается по `caps` пира (бит `voice`) и транспорту; несжатый
PCM никогда не по проводу.

**Провод.** `EXT VOICE_MANIFEST`: `[blobId u32][codec 1][rate 1][durMs u16]
[size u32][sha256 8][chunkCount u16]`; сами данные — `EXT BLOB_CHUNK/ACK` по
§5.4 (части, битмап, `MISSING`, resume по байт-офсету, финальный SHA-256).
Сохраняется/докачивается через mailbox (§5.3), т.е. получатель может быть
офлайн в момент отправки.

**Транспорт по типу звена:**
- **ESP32 ⇄ ESP32:** ESP-NOW (broadcast-флуд + ARQ), чанк ~222Б → 20 КБ
  ≈ 90 чанков; отложенно, надёжно. LoRa — только Codec2-профиль, с
  duty-cycle (§6).
- **App ⇄ App:** BLE-GATT (MTU 517, чанк 496Б) либо TCP/PusiServer; быстро.
- **App ⇄ ESP32:** **Android не умеет ESP-NOW** → только BLE-GATT (режим E)
  либо через PusiServer по интернету. Прямого ESP-NOW от телефона нет.
- **BLE-ADV (27Б/кадр):** голос невозможен — честный фолбэк
  «диктовка→текст→TTS» (в приложении уже есть), UI говорит, а не молчит.

**Надёжность.** Отправитель держит blob до полного ACK/SHA или TTL
(напр. 30 мин), каждая часть подтверждается битмапом, битые — REPAIR/перекачка,
целостность — SHA-256 всего клипа. Прогресс-UI, пауза/продолжение.

**Сервер.** PusiServer — наш собственный стек (MQTT/WS, §6), **без Xiaozhi**;
он может быть релеем и хранилищем голосовых (blob), но не обязан: прямой
BLE-GATT/ESP-NOW работает и без интернета.

## 6. Транспортные профили

| Транспорт | Макс. дейтаграмма | Режим | Адрес звена | Заметки |
|---|---|---|---|---|
| BLE-ADV (legacy) | 27Б кадр / 31Б AD | C | RPA | presence+короткий кадр, 1 хоп; релей через AD `PER1` |
| BLE-GATT | MTU 517 | E | RPA | коннект-ориентированный; DM/файлы/голос |
| ESP-NOW v1 | 250Б | E | STA MAC | broadcast-флуд, ch6, 19.5дБм, link-ACK |
| LoRa (Meshtastic/MeshCore как носитель) | ~200Б | E | — | **868 SRD + token-bucket duty-cycle**, не любительские полосы |
| MQTT / TCP (наш PusiServer) | ∞ | E | — | топики `pusi/<squadTag>/<nodeId>/{presence,msg,ack,mailbox,blob,voice}`; сервер — непрозрачный релей+хранилище; QoS1, retained presence, LWT |

**Сервер — свой, Xiaozhi не используем нигде.** Голосовой агент, ASR/TTS,
синхронизация и OTA — на нашем стеке (PusiServer: FastAPI + собственный
WS/MQTT-протокол). Отдельного «xiaozhi-совместимого» канала нет; ESP32-устройства
говорят с PusiServer по нашему протоколу, а меш-протокол (этот документ) от
сервера не зависит и работает без интернета.

Единый интерфейс (за образец `mesh_transport.h`):
`Start/Stop/Running/Ready/SetAdvert/SendFrame/SendEnvelope/Poll/Tick/OwnLink/Caps`.

## 7. Фазы реализации

> Порядок обязателен. Каждая фаза заканчивается зелёными host-тестами,
> сборкой и (где есть железо) bench-проверкой. Коммит на фазу.

- **Ф0. Спека и векторы.** Финализировать §3–6; сгенерировать golden-векторы
  (Python `cryptography`) на presence, кадры, envelope, routeTag, SACK/REPAIR,
  mailbox, blob; негативные кейсы. Заголовок `pusimesh_v2.h` + `test/`.
- **Ф1. Личность.** `nodeId` (генерация/персист), presence v2, карта
  `linkAddr→nodeId`, nonce от nodeId. Проверка: смена адреса не рождает
  нового гостя; кадры телефона открываются.
- **Ф2. Ядро кадров.** MeshFrame v2 + SEALED kinds (CANNED/TEXT/EMOTE/HELLO/
  READ/SACK/REPAIR/TEXT_LONG/CONTROL/CONFIRM), EXT-контейнер, IDENTITY, CAPS.
- **Ф3. Envelope + релей (ESP-NOW).** MeshEnvelope, managed flood, seen-cache,
  overhear, contention, last-mile, DM-ACK, routeTag.
- **Ф4. ARQ.** MeshReliable (окно/SACK/REPAIR/RTO), состояния доставки в UI.
- **Ф5. Почта/store-and-forward.** bounded mailbox + MSG_QUERY/SUMMARY/FETCH/
  CHUNK/ACK; «спроси соседа про непрочитанное».
- **Ф5.5. Индикатор батареи (UI, все прошивки и все устройства).** Заказчик,
  2026-10-18. В верхнем правом углу — векторная (нарисованная, не глиф)
  иконка батареи из четырёх секций; секции заполняются и меняют цвет по мере
  заряда/разряда (напр. красный→янтарный→жёлтый→зелёный), а поверх иконки —
  число процента, подобранное так, чтобы оставаться читаемым на любой из
  четырёх цветных секций (контраст текста и обводки, как у красного бабла
  сообщения в `ui_clear.cpp`). Один общий модуль (напр.
  `include/battery_gauge.h` + `src/battery_gauge.cpp`), единый для CYD, кубика
  и всех остальных бордов, с системным источником заряда (PMU/ADC уже есть в
  прошивке) и честным «нет данных» там, где батареи не читаются. Порядок:
  **после полного перехода на v2, до голосовых (Ф6).** Не отвлекаться на неё,
  пока v2 не завершён.
- **Ф6. Блобы (файлы/голос).** BLOB_*/VOICE_*; выбор транспорта; resume+sha;
  **голосовое 10–15 с** (§5.5) с Codec2-профилем для LoRa и Opus по умолчанию;
  mailbox-докачка офлайн-получателю.
- **Ф7. LoRa-носитель + сервер.** двусторонний LoRa-носитель (payload
  Meshtastic/MeshCore), MQTT/WS-топики **нашего PusiServer**, серверный
  релей/хранилище blob и голоса. Никакого Xiaozhi.
- **Ф8. Закалка.** fuzz/негатив, суточный soak, матрица interop (3 платформы),
  документация и страница в `/home/al/wiki`.

Критерий завершения v2: три платформы (PotSquad, Android, Desktop) в одном
скваде: presence без дублей, чат (латиница+кириллица, имена кириллицей),
эмоуты, DM, файл и **голосовое 10–15 с через хоп** (в т.ч. ESP32⇄ESP32),
почта «спроси непрочитанное», смена MAC/RPA не ломает ничего, всё стабильно
в суточном прогоне на 3+ узлах.

## 8. Тестирование и качество

- Чистые кодеки (`presence`, `frame`, `envelope`, `route`, `mailbox`, `blob`)
  компилируются на хосте и покрыты golden-векторами и негативами.
- Каждая фаза: `pio run -e cyd-ili9341` (или целевой env) + host-тесты +
  симулятор-рендеры UI (для прошивки).
- Никаких новых `malloc` в горячем радио-пути; статические буферы.
- Один коммит — одна фаза/подфаза, с осмысленным сообщением.
- Принципы Карпати: минимум сущностей, чистое отделять от радио, не
  добавлять абстракций без надобности, код читается как объяснение.
